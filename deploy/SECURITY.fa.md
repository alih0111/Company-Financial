# امنیت نسخهٔ آمادهٔ انتشار

تاریخ بررسی: ۲۰۲۶-۱۱-۰۷. این گزارش دربارهٔ کد و آزمون‌های محلی است؛ هنوز سرور، دامنه و انتشار عمومی وجود ندارد. دیتابیس و حساب‌های فعال دستگاه تغییر نکرده‌اند. آزمون‌های واقعی دیتابیس روی PostgreSQL جدا، درگاه محلی ۱۵۵۴۲ و نقش محدود `rfa_app` اجرا شدند.

## کنترل‌های اعمال‌شده

- **ورود و نشست:** در production، شناسهٔ تصادفی ۲۵۶ بیتی در کوکی `__Host-rfa_session` با Secure، HttpOnly، SameSite=Strict و Path=/ قرار می‌گیرد؛ فقط SHA-256 آن در دیتابیس ذخیره می‌شود. فرانت رمز نشست را نمی‌خواند یا در localStorage نمی‌گذارد. JWT قدیمی در production پذیرفته نمی‌شود. عمر مطلق ۱۲ ساعت، مهلت بی‌کاری ۳۰ دقیقه و سقف نشست هر حساب ۱۰ است. خروج، رکورد نشست را حذف می‌کند؛ تغییر نقش و غیرفعال‌شدن حساب در درخواست بعدی اثر دارد.
- **رمز عبور:** حساب جدید و مدیر جدید از Argon2id با ۶۴ MiB حافظه، سه تکرار، یک مسیر پردازش، salt تصادفی ۱۶ بایتی و خروجی ۳۲ بایتی استفاده می‌کنند. رمز جدید حداقل ۱۵ نویسه و حداکثر ۷۲ بایت است؛ چند الگوی رایج و تکرار کامل یک نویسه رد می‌شوند. این فهرست، پایگاه کامل رمزهای افشاشده نیست. bcrypt حساب‌های قدیمی همچنان خوانده می‌شود؛ رمز یا hash آن حساب‌ها خودکار تغییر نکرده است. پارامترهای hash ورودی محدودند تا مقدار خراب، حافظهٔ نامحدود درخواست نکند.
- **مقابله با سوءاستفاده:** سقف درخواست بر اساس IP و برای چت بر اساس کاربر، محدودیت تلاش ورود بر اساس شناسهٔ حساب و سقف هم‌زمانی پردازش رمز و ایمیل وجود دارد. کد ثبت‌نام تصادفی، ده دقیقه معتبر، دارای سقف پنج تلاش و فقط یک بار قابل مصرف است. ثبت‌نام عادی نمی‌تواند نقش مدیر بگیرد. تمام این محدودکننده‌ها برای یک replica طراحی شده‌اند.
- **درخواست مرورگر:** درخواست نوشتن با کوکی به Origin معتبر نیاز دارد؛ در production مبدأ باید HTTPS باشد. بدنهٔ غیرخالی باید JSON باشد و بدنهٔ واقعی، شامل chunked، حداکثر دو MiB است. حالت توسعه فقط برای پروکسی محلی Vite است. مسیرهای مدیریت در router نقش مدیر می‌خواهند. اجراکننده‌های قدیمی دریافت از URL در production غیرفعال‌اند.
- **دادهٔ کاربران:** عملیات سبد به شناسهٔ کاربر احرازشده محدود است؛ درخواست کاربر دیگر اجازهٔ حذف نمی‌گیرد. نوشتن هم‌زمان با تراکنش و قفل حساب انجام می‌شود. نام دارایی از مرجع canonical خوانده می‌شود. watchlist و هشدارهای محلی برای هر نام کاربری کلید جدا دارند. متن خارجی خروجی CSV در برابر اجرای فرمول spreadsheet محافظت می‌شود.
- **نمایش و فایل‌ها:** CSP، منع iframe، nosniff، COOP/CORP و جلوگیری از cache پاسخ‌های حساب اضافه شده‌اند. فایل‌ها با ریشهٔ محصورشدهٔ سیستم‌عامل ارائه می‌شوند؛ مسیر خروج از ریشه و symlink بیرونی پذیرفته نمی‌شود. پسوندهای خصوصی و فایل‌های موقت منتشر نمی‌شوند. خروجی عمومی پژوهش باید پیش از انتشار فقط شامل دادهٔ قابل انتشار باشد.
- **خطا و گزارش:** پاسخ‌های خطای ۵۰۰ به بالا در production عمومی‌اند و شناسهٔ پیگیری دارند. گزارش دسترسی جدید فقط شناسهٔ درخواست، روش، الگوی مسیر، وضعیت و مدت را ثبت می‌کند؛ query، بدنه، کوکی، رمز، Authorization و متن panic در آن چاپ نمی‌شوند. خطاهای مدل زبانی بدنهٔ پاسخ تأمین‌کننده یا کلید API را به کاربر بازنمی‌گردانند.
- **مدل زبانی:** نقش system/tool از پیام کاربر پذیرفته نمی‌شود؛ تعداد و اندازهٔ پیام‌ها و پاسخ تأمین‌کننده محدودند. درخواست تأمین‌کننده redirect را دنبال نمی‌کند و آدرس آن در production باید HTTPS باشد. ابزارهای تعریف‌شدهٔ سرور باقی مانده‌اند؛ این کنترل‌ها تضمین صحت پاسخ مدل نیستند.
- **انتشار:** برنامه با کاربر غیر root و بدون قابلیت‌های Linux اجرا می‌شود؛ دیتابیس و API درگاه عمومی ندارند. Caddy ورودی عمومی و HTTPS است و API مدیریتی آن بسته است. پروکسی مورد اعتماد IP مشخص دارد. آدرس پیش‌فرض اجرای مستقیم Go فقط loopback است. تصویر Docker شامل env و حساب‌های محلی نیست. کلیدهای انتشار تصادفی و فایل تنظیمات خصوصی‌اند.

اصول نشست و hash رمز با [راهنمای نشست OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) و [راهنمای ذخیرهٔ رمز OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) بررسی شدند.

## محدودیت برداشت داده

کنترل دسترسی فایل‌های پژوهش، سهمیهٔ روزانهٔ ماندگار، جدول‌های صفحه‌ای، نمای خلاصه و مدیریت مجوز کاربران به این نسخه اضافه شده‌اند. **[DATA_PROTECTION.fa.md](DATA_PROTECTION.fa.md)** راهنمای رفتار جدید و migration شمارهٔ ۱۵۰ است. مخزن GitHub در بررسی این مرحله عمومی بود؛ خصوصی‌کردن آن و registry تصویر، بخشی از پیش‌نیاز انتشار است.

## ارتقای دیتابیس موجود

نصب تازه همهٔ ۲۲ migration را خودکار اعمال می‌کند. برای دیتابیس موجود، پیش از اجرای بک‌اند جدید، پشتیبان بگیرید و فقط migration افزایشی زیر را اعمال کنید؛ SQLهای ایجاد اولیه را دوباره اجرا نکنید. فرمان‌های زیر مخصوص نام‌های همین Compose هستند:

```bash
python3 deploy/backup.py
docker compose --env-file deploy/.env exec -T db psql -U rfa_owner -d company_financial -v ON_ERROR_STOP=1 -f /schema/140_auth_sessions.sql
docker compose --env-file deploy/.env exec -T db psql -U rfa_owner -d company_financial -v ON_ERROR_STOP=1 -c 'GRANT SELECT, INSERT, UPDATE, DELETE ON auth.sessions TO rfa_app;'
docker compose --env-file deploy/.env up -d --build --wait
```

جدول جدید hash نشست‌ها را نگه می‌دارد؛ خواندن و نوشتن آن برای نقش برنامه لازم است. migration شمارهٔ ۱۵۰ و مجوز جدول‌های آن را نیز طبق راهنمای حفاظت داده اعمال کنید. پس از ارتقا، کاربران دوباره وارد می‌شوند. فرانت و بک‌اند باید با هم ارتقا یابند. برای دیتابیس خارج از Compose، همین فایل SQL را با ابزار اتصال امن و نقش مالک خودتان اعمال کنید؛ اطلاعات اتصال را در پیام یا Git قرار ندهید. این migration روی دیتابیس فعال دستگاه اجرا نشده است.

فرانت و API را روی یک مبدأ HTTPS قرار دهید. حالت HTTP با IP فقط برای بررسی سلامت نصب است و برای ورود عمومی آماده نیست. پس از بازیابی پشتیبان کامل، پیش از بازکردن سرویس، محتویات `auth.sessions` را حذف کنید تا نشست‌های لغوشدهٔ قدیمی دوباره معتبر نشوند.

## اسرار حذف‌شده از منبع

اطلاعات اتصالِ نوشته‌شده در ۱۸ فایل پژوهشی حذف و با متغیر `CDF_RESEARCH_DSN` جایگزین شد. اجرای آن اسکریپت‌ها اکنون به تنظیم صریح این متغیر در محیط امن نیاز دارد؛ مقدار پیش‌فرضِ حاوی رمز ندارند. ابزار `scripts/check_secrets.py` منبع را بررسی می‌کند، محل یافته را گزارش می‌دهد و مقدار راز را چاپ نمی‌کند؛ در CI نیز فعال است. بررسی الگوها همهٔ انواع راز را تشخیص نمی‌دهد.

**اگر رمزهای قبلی هنوز معتبرند، باید در PostgreSQL و هر محل استفادهٔ همان رمز تعویض شوند.** حذف از فایل جاری، نسخهٔ تاریخچهٔ Git یا cloneهای دیگر را پاک نمی‌کند. رمز واقعی، حساب فعال و تاریخچهٔ مخزن در این کار تغییر نکرده‌اند. پس از تعویض، اتصال‌های مجاز را با رمز تازه تنظیم و دسترسی رمز قدیمی را بررسی کنید. بازنویسی تاریخچه هم جای ابطال رمز را نمی‌گیرد.

## شواهد بررسی

- آزمون‌های Go با PostgreSQL جدا و نقش غیر superuser موفق‌اند: ورود، ثبت‌نام، نقش‌ها، جداسازی سبد، شش نوشتن هم‌زمان، انقضای نشست و لغو نشست. یک آزمون با سرور TLS واقعیِ محلی و cookie jar، ورود، خواندن حساب و خروج را بررسی می‌کند؛ فقط تزریق هدر در recorder نیست.
- آزمون‌های امنیت درخواست، CSRF/Origin، درخواست حجیم chunked، فرم غیر JSON، سقف هم‌زمانی، نقش پیام مدل، CSV و عدم افشای جزئیات در خطا و گزارش موفق‌اند. آزمون خروج از ریشه با symlink روی میزبان فاقد مجوز ساخت symlink ممکن است skip شود؛ CI Linux نیز آن را اجرا می‌کند.
- ساخت اجرایی Linux با CGO غیرفعال و ۱۶ آزمون پایتون برای قفل فرایند، FactorMix و ReportFlow موفق‌اند.
- ساخت TypeScript/Vite، تمام ۶۱ آزمون فرانت، lint با صفر خطا و بررسی کامل npm موفق‌اند. `npm audit --audit-level=moderate` صفر هشدار در همهٔ سطوح گزارش کرد. یک هشدار موجود fast refresh در FactorMix و هشدار اندازهٔ chunk نمودار باقی است.
- `pip-audit` برای ۵۳ وابستگی حل‌شدهٔ فایل انتشار صفر آسیب‌پذیری گزارش کرد. این نتیجه مربوط به حل وابستگی در میزبان Windows است؛ تصویر Linux ساخته‌شده هنوز اینجا وجود ندارد که جدا بررسی شود.
- Go به toolchain نسخهٔ 1.26.10 و وابستگی‌های اصلاح‌شده ارتقا یافت؛ درایور قدیمی SQL Server با نسخهٔ نگهداری‌شدهٔ Microsoft جایگزین شد. بررسی OSV برای هدف Linux، ۳۷ ماژول زمان اجرا را شامل شد و advisory مؤثر بر packageهای واردشده پیدا نکرد. هشدار `GO-2026-5932` دربارهٔ زیرشاخه‌های OpenPGP در `golang.org/x/crypto` همچنان گزارش می‌شود؛ آن packageها وارد برنامه نشده‌اند. نتیجهٔ بررسی ماژول به معنی پاک بودن همهٔ زیرشاخه‌های آن نیست.
- ابزار محلی `govulncheck` نتوانست پایگاه `vuln.go.dev` را دریافت کند؛ سرور پاسخ ۴۰۳ داد. بنابراین بررسی محلی کاملِ نمادها و call graph انجام نشده است. `scripts/audit_go_dependencies.py` بررسی جداگانهٔ OSV بر اساس packageهای واردشده است. CI اجرای سخت‌گیرانهٔ govulncheck و آزمون race را نگه می‌دارد؛ اجرای موفق CI هنوز مشاهده نشده است.
- actionهای GitHub به commit مشخص بسته شده‌اند؛ CI علاوه بر آزمون‌ها، رازهای منبع، npm، Python، Go و ساخت و smoke کل Compose را بررسی می‌کند.

جزئیات آماده‌سازی و آزمون‌های دیگر در [VERIFICATION.fa.md](VERIFICATION.fa.md) است. نتیجهٔ صفر اسکن فقط نبود یافتهٔ شناخته‌شده در دامنه و تاریخ همان اسکن است.

## بررسی‌های وابسته به سرور مقصد

Docker Engine روی این دستگاه موجود نیست؛ ساخت و اجرای واقعی کانتینر، گواهی دامنه، تحویل SMTP، بازگردانی کامل پشتیبان روی مقصد، آزمون بار و آزمون نفوذ عمومی هنوز انجام نشده‌اند. بررسی بصری کامل مرورگر هم تکمیل نشده است. این کار جای آزمون نفوذ مستقل را نمی‌گیرد و MFA مدیر هنوز پیاده نشده است.

پیش از بازکردن ثبت‌نام عمومی: رمزهای قدیمی معتبر را باطل کنید، migration را اعمال کنید، HTTPS و ارسال ایمیل را عملاً بیازمایید، از حساب معمولی و مدیر ورود و خروج بگیرید و بازیابی پشتیبان را روی مقصد جدا انجام دهید. سیستم‌عامل سرور و تصاویر پایه نیز باید به‌روز و پایش شوند. محدودکننده‌ها برای مقابله با DDoS بزرگ کافی نیستند؛ هنگام انتخاب میزبان، ظرفیت و محافظت شبکهٔ آن هم باید بررسی شود.
