# TF-04C-PILOT — دریافت عمومی محدود با receipt قابل بازپخش

این پلن پیشنهادی مرحلهٔ بعد از پذیرش TF-04B-CLOSE است. با سپردن آن برای اجرا، دامنهٔ کار شامل GET عمومی محدود زیر است؛ در بازبینی TF-04B-CLOSE هیچ شبکه‌ای اجرا نشده است. هدف، اثبات مسیر دریافت امروز → receipt → parser → بازپخش روی مقصد ایزوله است؛ نه آمادگی حساب یا تصمیم خرید.

## مرز کار

- ابتدا `docs/paper_portfolio_delivery/task-tf04b-close/review/REVIEW.fa.md` را بخوان. اصلاحات پذیرفته‌شدهٔ context، cutoff، parser و حسابداری را بازطراحی نکن.
- خروجی جدید فقط زیر `docs/paper_portfolio_delivery/task-tf04c-pilot/<unique-run>/`. از overwrite مقصد موجود جلوگیری کن. cache/resume/raw جاری، DB، public، ranking، قواعد، حساب، ledger، scheduler و index ثابت بمانند.
- تنها **یک هویت از universe قفل‌شده**: غاذر، با company_id و نماد دقیق برگرفته از identity map. انتخاب آن صرفاً نمونهٔ مهندسی به‌دلیل شواهد محلی قبلی است؛ هیچ توصیهٔ سرمایه‌گذاری یا کاهش universe نیست. دو feed مالی و فروش بررسی شوند.
- سقف کل **12 درخواست HTTP واقعی**، یک درخواست هم‌زمان، timeout محدود. redirect و retry هم جزء سقف‌اند. بودجهٔ درخواست را پیش از ارسال enforce کن؛ پارامتر یا helper دیگری نباید بتواند از آن عبور کند. این سقف فقط هزینهٔ آزمایش را محدود می‌کند، معیار کفایت داده نیست.
- فقط endpointهای عمومی رسمی که collector موجود استفاده می‌کند؛ بدون token، login، مرورگر برای عبور از challenge، proxy یا دورزدن محدودیت. cooldown جاری را از دادهٔ موجود رعایت کن. با CAPTCHA یا 429 پایلوت را متوقف و شاهد را ثبت کن؛ retry خودکار نداشته باش. رسیدن به سقف، timeout و نبود دسترسی نتیجهٔ محدود/مسدود هستند، نه مجوز دورزدن کنترل.

## ۱. استفادهٔ محدود از مسیر موجود

مرجع collector: `ranking_research/future_eval_v12_30/acquire_codal_incremental.py`؛ parser: `prepare_codal_inputs.py`.

collector اصلی OUT و cache/resume مشترک دارد؛ main آن را مستقیم با مقصدهای پیش‌فرض اجرا نکن. adapter کوچک یا پارامترهای ایزولهٔ لازم را اضافه کن؛ هیچ چرخهٔ عملیاتی اجرا نشود. تمام نوشتن‌های helperها نیز باید به run جدید محدود شوند. اگر لازم است cache قدیمی خوانده شود، فقط خواندن یا کپی کوچک در run مجاز است؛ زمان آن را receipt این invocation جا نزن. قبل از اولین GET، حالت dry-run باید هویت، feed، بازهٔ query، مقصدها و سقف HTTP را نشان دهد.

بازهٔ کشف از watermark و سیاست موجود collector گرفته شود و مبنایش ثبت شود؛ تاریخ ثابت 24 اکتبر یا ساعت ساختگی به کار نبر. صفحات search، Total، شمارهٔ صفحه، هویت و correction chain را تا جایی که بودجه اجازه می‌دهد ثبت کن. اگر همهٔ صفحات لازم دریافت نشدند، `census_complete=false` باشد. «صفحهٔ اول موفق» یا «بدنهٔ cache موجود» معادل نبود اطلاعیهٔ جدید نیست.

از نتایج همین دریافت، حداکثر یک گزارش مالی و یک فروش مناسب برای آزمایش parser انتخاب کن؛ علت انتخاب و گزارش‌های دریافت‌نشده را بنویس. صفحات وابستهٔ مالی هم در سقف مشترک‌اند. این محدودیت به معنی کامل بودن پوشش مالی نماد نیست.

## ۲. receipt صادقانه و متصل به bytes

برای هر تلاش شبکه، run_id، هویت/feed، URL و query، زمان آغاز/دریافت UTC timezone-aware واقعی، وضعیت HTTP یا خطای transport، raw path، اندازه و SHA-256 ثبت شود. دامنهٔ hash روشن باشد: bytes ذخیره‌شده، payload پس از decompression و متن نرمال‌شده متفاوت‌اند. برای تلاش بدون پاسخ، body یا زمان دریافت موفق نساز.

manifest همان invocation به rawها و receipt متصل باشد. HTTP 200 با بدنهٔ challenge موفقیت داده محسوب نشود. receipt امروز فقط دریافت امروز را اثبات می‌کند؛ آن را به انتشار قدیمی، cache قدیمی، `observed_at` یا تصمیم گذشته نسبت نده. زمان انتشار منبع جداگانه حفظ شود. هویت، واحد، basis، parent و publication mismatch همچنان سخت‌گیرانه کنترل شوند.

parserهای موجود را روی snapshot جدید اجرا کن. admission صفر، همهٔ خروجی‌های قابل parse held و readiness کلی false بماند. نبود صفحهٔ لازم یا رد parser با علت صریح ثبت شود؛ حتی دادهٔ ردشده از ممیزی ورودی حذف نشود.

## ۳. پذیرش و آزمون کم‌هزینه

- پیش از live، fixture آفلاین برای مقصد ایزوله، سقف درخواست، توقف 429/challenge، ثبت hash receipt و تمایز cache/دریافت جدید کافی است. آزمون‌های موجود فقط به اندازهٔ مسیر تغییرکرده اجرا شوند؛ suite حسابداری و بازسازی بازار/wrapper لازم نیست.
- در صورت دسترسی موفق، همان capture با شبکهٔ ممنوع replay شود؛ مجموعهٔ ورودی و نتیجهٔ parse/رد و علت held ثابت باشد. زمان اجرای replay می‌تواند متفاوت باشد، receipt منبع نباید تغییر کند.
- وضعیت‌ها جدا باشند: `implementation_tests`، `live_acquisition`، `source_receipt_binding`، `census_completeness`، `parser_replay` و `decision_readiness`. PASS نرم‌افزار را PASS دسترسی زنده یا آمادگی تصمیم معرفی نکن.
- اگر cooldown/challenge/429 مانع شد، یک تحویل محدود با raw و علت و درخواست‌های انجام‌شده کافی است؛ با retry بیشتر یا گزارش‌سازی مکرر برای PASS تلاش نکن.
- baseline کوچک پیش/پس روی ورودی‌ها و مقصدهای مشترکی که کد ممکن است لمس کند ثبت شود. همهٔ خروجی‌های تحویل و کدهای تغییرکرده در manifest کوچک باشند؛ pytest temp و بستهٔ بازار قبلی را کپی نکن.

## ۴. خروجی تصمیم‌ساز برای ادامه

علاوه بر REPORT کوتاه، result و manifest، یک `NEXT-DECISION.fa.md` حداکثر یک صفحه بده:

1. چه چیزی با receipt امروز ثابت شد و چه چیزی همچنان نامعلوم است؟
2. تعمیم مسیر به 254 هویت چه داده/هزینه‌ای لازم دارد؟ تعداد identity/feed را تعداد HTTP ننام؛ برآورد را با فرض صفحات و بدنه‌ها جدا بنویس.
3. از موانع باقی‌مانده، کدام با دریافت بیشتر حل می‌شود و کدام نیازمند تصمیم سیاستی است؟ تازگی قیمت/مالی و پوشش اقدام شرکتی را با معیار مصوب موجود گزارش کن؛ اگر مصوب نیست، پیشنهاد و اثرش را مشخص کن و آن را روی قواعد اعمال نکن. شرط قدیمی را بی‌صدا حذف نکن.

تحویل باید یک فرمان dry-run، فرمان اجرای محدود و فرمان replay آفلاین قابل بازتولید داشته باشد. پس از همین پایلوت و گزارش متوقف شو؛ دریافت گستردهٔ 508 جفت، انتقال candidateها، ساخت تصمیم، preview/fill و فعال‌سازی در این مأموریت نیستند.
