محل کار `D:/RFA/Company-Financial` است. این مأموریت را تا پیاده‌سازی و اجرای آفلاین کامل انجام بده. هدف خروجی قابل مصرف از دادهٔ موجود و فهرست کسری دقیق است؛ وضعیت تصمیم ممکن است همچنان BLOCKED بماند. ابتدا `docs/paper_portfolio_delivery/task-tf04a/review-finish/REVIEW.fa.md` و `verification.json` و پلن پیشنهادی TF-04B داخل finish-20261025 را بخوان. این سند محدودهٔ اجرای فعلی را تعیین می‌کند.

## حدود

شبکه، token، DB، scheduler، preview/fill، فعال‌سازی، تغییر حساب، دفتر رسمی و انتشار public ranking انجام نده. مدل/وزن/coverage/universe/O00 و قراردادهای قفل‌شده تغییر نکنند. کارهای هم‌زمان و index را حفظ کن؛ stage/reset گسترده نکن. خروجی‌ها فقط در `docs/paper_portfolio_delivery/task-tf04b-local/` و یک run تازه و یکتا زیر آن باشند. شواهد قبلی به‌ویژه reviewها byte-exact بمانند.

تغییر محدود ابزار تشخیص و builder برای رفع metadata و امکان مقصد صریح مجاز است؛ refactor موتور یا تغییر factor/scoring مجاز نیست. ۱۸۵ آزمون را بی‌دلیل تکرار نکن؛ آزمون‌های تشخیص و آزمون‌های مرتبط با مسیرهای تغییرکرده کافی‌اند. اگر تغییر shared code دامنهٔ بیشتری دارد، آزمون مرتبط را با علت انتخاب کن.

## ۱. دو ایراد بازبینی را در ابتدا ببند

- manifest بازار باید با declaration پین‌شده مقایسه شود. registration سالم همراه manifest خراب/مفقود/بدون declaration نباید market-package hash-bound بدهد. اتصال rawهای referenced به digest مورد انتظار را با verifier موجود یا کنترل محدود تکمیل کن؛ hash registration، manifest، raw و اعتبار زمان نتایج جدا دارند. اگر raw هنوز بررسی نشده وضعیت صریح NOT_VERIFIED بده، نه اثبات کلی provenance.
- آزمون از مسیر assess برای سالم، manifest mismatch، raw mismatch و declaration مفقود بنویس. زمان invalid/بدون timezone/آینده/پس از تصمیم را نیز از همین مسیر با fixture کوچک بسنج؛ ساعت واقعی CLI قابل جعل نباشد. اعتبار منشأ و ترتیب timestamp مستقل گزارش شوند.
- دربارهٔ غاذر 1569119، raw bytes با lineage برابر نیست اما SHA متن UTF-8 با یکسان‌سازی پایان‌خط‌ها برابر است. producer digest را از کد دنبال کن؛ raw_bytes_sha256، normalized_text_sha256، روش normalization و lineage_digest را جدا ثبت کن. در صورت اثبات روش، تطبیق محتوای متن مجاز است؛ ادعای byte-exact نکن. با digest بدون قرارداد معلوم، UNKNOWN بده. گزارش/نتیجهٔ اصلاحی را با مرجع به شاهد قبلی در بستهٔ جدید بنویس؛ نیازی به بازنویسی تاریخچه نیست.

## ۲. reuse واقعی، نه شمارش دوبارهٔ manifest

فقط همان cycle `paper-cycle-20261024T190004112005Z-d1278aa0` و فایل‌های raw/cache ارجاع‌شده از شواهد TF-04A را بخوان. پیش از parse، snapshot محلی ورودی‌ها و digest واقعی زمان مشاهده را در run جدید ثبت کن. receipt تاریخی نساز؛ mtime نیز receipt نیست.

- ۵۷ raw مالی همان cycle، ۱۶ body مالی دیگر و ۱۱ body فروش فهرست‌شده را با شناسه‌ها deduplicate کن؛ شمار نهایی از فایل‌ها حاصل شود و ۸۴ عدد اجباری پذیرش نیست.
- gzip/decompression، نوع پاسخ، identity، tracing_no، period و statement type را با validator/parser موجود بررسی کن. CAPTCHA/HTML خطا حتی HTTP200 یا digest سالم دادهٔ مالی معتبر نیست. خروجی parse و facts مورد استفاده را به raw دقیق وصل کن. اگر parser قابل reuse نیست، علت و کسری روشن بده؛ صرف شمارش body_evidence را parsed PASS ننام.
- نتیجه برای هر report: منبع، hashهای compressed/decompressed یا متن با روش روشن، metadata، واقعاً parsed/reusable بودن، علت رد و عوامل مصرف‌کننده. metadata موجود/body مفقود، body نامعتبر و تاریخ دریافت مجهول وضعیت‌های جدا هستند.
- برای غاذر 1569119 زنجیرهٔ raw→facts→factorهای مصرفی را با حداقل نمونهٔ واقعی نشان بده؛ تپمپی1608939 و تاصیکو1601930 را بدون شاهد جدید از UNKNOWN به PASS نبر.
- نبود receipt تاریخی به‌تنهایی مانع seal واقعی امروز و استفاده برای تصمیم آینده نیست. freshness، جامعیت اطلاعیه و کیفیت عوامل باید مستقل گزارش شوند. این مرحله هنوز تصمیم صادر نمی‌کند.

## ۳. metadata صحیح و مقصد ایزوله را واقعاً اجرا کن

- در مسیر v12-37 که builder v12-35 را صدا می‌زند، dataset/evaluation/cutoff/source dates نباید با ثابت‌های نسخهٔ قدیمی overwrite شوند. از ورودی‌های معتبر همان run استخراج و قبل از نوشتن consistency را کنترل کن. آمار کل آرشیو و انتخاب panel دو فیلد/دامنهٔ مستقل باشند.
- قرارداد cutoff باز/بسته را از selector واقعی دنبال کن؛ تبدیل نیمه‌شب انحصاری به آخر روز شامل، تنها با اثبات قرارداد زمانی انجام شود. fixture انتشار دقیقاً روی مرز باید نتیجهٔ مشخص داشته باشد. از tolerance عمومی 1µs به‌جای قرارداد استفاده نکن.
- قبل از اجرای builder همهٔ مقصدهای public/default/DB را بررسی کن؛ مقصد صریح run تازه تا توابع پایین‌دست برسد. اگر wrapper خروجی ثابت دارد، آن مسیر را با override واقعی ایزوله کن. روی دادهٔ pinned موجود بازسازی آفلاین را اجرا کن و validator قفل‌شده را در همان run اجرا کن؛ فایل‌های اصلی دست‌نخورده باشند.
- آزمون same-input ثابت کند اصلاح metadata به‌تنهایی عامل‌ها، score و ترتیب P1/P3 را تغییر نمی‌دهد. اگر اتصال raw معتبر دادهٔ تازهٔ قابل مصرف می‌دهد، آن را در خروجی مجزای candidate با تفاوت عامل‌های توضیح‌پذیر بساز؛ قرارداد همچنان روی همهٔ ۲۵۴ هویت اعمال شود. دادهٔ ناقص را برای حفظ رتبه یا اجبار PASS جعل نکن.
- ساخت خروجی محلی با دادهٔ قدیمی «ranking تازهٔ بازار» نیست. تاریخ ارزیابی را بدون قیمت/دادهٔ مناسب به امروز جلو نبر و PREPARATION_UNCONFIRMED را صرف پاس شدن validator تغییر نده.
