## اصلاحات این نوبت

### ۱. اعتبارسنج حساب را کامل کن

در `ranking_research/paper_account_store.py` برای همین عملیات فعلی یک schema حداقلی صریح تعریف کن. فیلدهای لازم پول/دارایی/رویداد و accounting با default صفر یا `if accounting` از اعتبارسنجی فرار نکنند. سازگاری با schema حساب فعلی حفظ شود؛ برای آزمایش یا مهاجرت آن را ننویس.

- نقد، ارزش دارایی و هزینه نامنفی؛ تعداد صحیح نامنفی؛ پول طبق policy فعلی تومان صحیح باشد. `bool`، کسر، مقدار غیرمتناهی و رشتهٔ نامعتبر را به عدد معتبر تبدیل و بی‌صدا ذخیره نکن. P&L می‌تواند منفی باشد.
- `holdings_value_toman` برابر جمع دارایی، NAV برابر نقد+دارایی، و **خودِ `accounting.profit_loss_toman`** برابر NAV−سرمایه−جریان خارجی و realized+unrealized باشد.
- فیلد اختیاری موجود مثل realized/external در دامنهٔ فعلی می‌تواند default مشخص داشته باشد؛ فیلد ضروری نباید چنین شود. برای این مأموریت دفتر دوبل، فروش یا schema عمومی پیچیده نساز.
- فیلدهای لازم holding و event را بررسی کن. شناسهٔ خالی/تکراری، قیمت یا ارزش نامعتبر و حساب ناسازگار نباید replace شوند.
- تست‌های منفی را از یک حساب **کامل و معتبر** بساز و هر بار فقط یک فیلد را خراب کن تا خطای دیگری نقص را پنهان نکند.

حداقل شواهد: سودوزیان نمایشی غلط با باقی ارقام صحیح، نقد −۰٫۵، نقد bool یا رشته/کسر ناسازگار، NaN/Infinity، فقدان accounting/فیلد ضروری، NAV غلط و تعداد غیرصحیح؛ در هر رد، bytes حساب قبلی ثابت باشد.

### ۲. تاریخچهٔ رویداد را در مسیر مشترک محافظت کن

`read_modify_write` اکنون از رویدادهای قبل reference نگه می‌دارد؛ تغییر nested در mutation باعث تغییر هم‌زمان مبنای مقایسه می‌شود. از snapshot مستقل استفاده کن و حذف، تغییر payload، تغییر شناسه یا جابه‌جایی رویدادهای قدیمی را رد کن؛ رویداد جدید فقط در انتهای تاریخچه افزوده شود.

محافظت باید در مسیر مشترک commit همهٔ entrypointها شامل decision، fill، observation/expiry و mark اعمال شود؛ اصلاح helper استفاده‌نشده کافی نیست. می‌توانی API مشترک فعلی را تکمیل کنی یا callerها را به transaction آن متصل کنی. قفل باید قبل از خواندن مبنا تا پایان validate/replace برقرار بماند. از nested lock غیرقابل بازگشت و API عمومیِ نوشتنِ بدون قفل جلوگیری کن؛ موتور موازی نساز.

تست لازم: mutation nested رویداد قبلی، حذف و جابه‌جایی آن رد و bytes حفظ شوند؛ افزودن رویداد معتبر موفق باشد؛ map نویسنده‌ها با اشاره به تابع مشترک واقعی در گزارش بیاید. این بخش هنوز مسئول افزودن replay عملیاتی fill نیست.

### ۳. گردکردن mark را با خرید هماهنگ کن

`check_paper_account.py` در mark هنوز `int(round(...))` دارد. تبدیل ریال/تومان، gross/fee/value را طبق policy `ROUND_HALF_UP` مشترک و بدون وابستگی نامطمئن به خطای float انجام بده؛ قرارداد نرخ هزینه، lot و تعداد را تغییر نده.

شاهد مستقل: حساب معتبر با یک سهم و close جدید ۱٬۰۰۵ ریال باید دارایی ۱۰۱ تومان نشان دهد. با سرمایهٔ ۱۰۰٬۰۰۰، cash=۹۹٬۸۹۹، cost=۱۰۰ و fee=۱، بعد از این mark باید NAV=۱۰۰٬۰۰۰ و P&L=۰ شود. علاوه بر این مرز نیم‌تومان، fixture خرید قبلی ۸۰۶ سهم و P&L=−۴۹۷ باید برقرار بماند.

### ۴. فایل‌های لازم واقعاً قابل تحویل باشند

ماژول جدید store و دو فایل decision/check زیر `.gitignore` پنهان‌اند. برای **همین فایل‌های سورس لازم** و تست‌های تازه استثنای محدود ایجاد کن. هیچ پوشهٔ خروجی/آرشیو/credential را عمومی unignore نکن؛ `git add -f .` یا stage کلی نکن. commit/push در این مأموریت لازم نیست.

با `git check-ignore` و `git status --short --untracked-files=all` نشان بده فایل لازم دیگر بی‌صدا حذف نمی‌شود؛ فایل‌های جدید را جدا از diff فایل‌های tracked در گزارش فهرست کن. برای artifactهای تحویل هم فهرست مسیر/اندازه/hash بده تا بازبینی فقط متکی بر `git diff` نباشد.

## محدودیت دامنه و آزمون

- حساب جاری، دفتر رسمی، scheduler، شبکه، مدل‌های P1/P3، وزن‌ها، قواعد اقتصادی 1.2.0، شناسه‌های موجود و مبدأ O00 تغییر نکنند. هیچ backtest جدید لازم نیست.
- replay عملیاتی fill و crash/concurrency کامل در **۰۱B** بسته می‌شوند. آن‌ها را در نتیجهٔ این مرحله PASS اعلام نکن؛ برای این نوبت API ذخیره‌سازی و تست‌های لازم آن را درست کن.
- schema حداقلی جدید ممکن است fixture ناقص قدیمی atomic replace را رد کند؛ آن fixture را معتبر کن و assertionهای اتمی‌بودن و عدم نوشتن را حفظ کن. آزمون مشکل‌دار را صرفاً حذف یا skip نکن.
- تست‌های entrypoint باید تمام مسیرهای ACCOUNT/RUN/PUBLIC و ورودی‌ها را به temporary directory هدایت کنند؛ از defaultهای فایل واقعی استفاده نکنند.

فرمان پایه:

```powershell
& .venv/Scripts/python.exe -X utf8 -m pytest ranking_research/tests/test_paper_account_atomic.py ranking_research/tests/test_paper_cycle_http.py -q
```

تست‌های متمرکز جدید را به دامنهٔ اجرا اضافه و فرمان دقیقشان را گزارش کن. probe بازبینی را می‌توانی برای مقایسه اجرا کنی، اما به سبزبودن exit code آن اکتفا نکن. پس از اصلاح API اگر probe نیازمند سازگارسازی بود، نسخهٔ جدا با توضیح بساز؛ شواهد قبلی را overwrite نکن. تست ساعت موتور آینده نامرتبط با این مأموریت است.
