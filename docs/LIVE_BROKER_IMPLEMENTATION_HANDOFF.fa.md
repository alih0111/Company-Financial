# دستور اجرای نهایی: آماده‌سازی RFA برای پیشرو و چند کارگزاری

این فایل را کامل به مدل مجری بدهید. مرجع تحلیل: `docs/LIVE_BROKER_READINESS_PLAN_2026-11-13.fa.md`. این دستور برای اجرای مرحله‌ای مهندسی است؛ فعال‌سازی معاملهٔ واقعی بخشی از تحویل اولیه نیست.

## مأموریت و دامنه

در پروژهٔ `D:\RFA\Company-Financial` کار کن. هدف، سامانهٔ قابل بازسازی و قابل حسابرسی برای استراتژی منتخب FactorMix ماهانه ۱۵، اتصال اول کارگزاری پیشرو و قابلیت افزودن کارگزاری‌های دیگر است. برنامه را دوباره از صفر ننویس؛ شواهد لازم را بخوان و بسته‌های زیر را به ترتیب پیاده‌سازی کن. هر بسته باید کد، آزمون رفتاری مرتبط و نتیجهٔ مستند داشته باشد.

فعلاً توسعهٔ آفلاین، محیط آزمایشی، اتصال فقط‌خواندنی و آماده‌سازی paper/simulation در دامنه است. هیچ سفارش واقعی، لغو سفارش واقعی، انتقال وجه، فروش دارایی فعلی یا فعال‌کردن اجرای live انجام نده. ارائهٔ مشخصات ورود یا بازبودن مرورگر به معنی اجازهٔ معامله نیست. برای ادامهٔ کارهای مستقل از اتصال و سرمایه، تأیید تکراری نخواه.

اگر تنها به فایل‌ها دسترسی داری، مراحل آفلاین را کامل انجام بده و بررسی واقعی پیشرو را `UNKNOWN` نگه دار. نبود دسترسی کارگزاری مانع ساخت قرارداد، adapter ساختگی، دفتر، ریسک و تست نیست. شواهد مصنوعی را به‌جای اتصال موفق ارائه نکن.

## واقعیت‌های شروع؛ دوباره با workspace تطبیق بده

- مدل منتخب: `RFA-FactorMix-033-M15-Buffer8-v1.0.0` در `strategy_registry/selected_strategy.json`؛ اجرای کارگزاری خاموش است.
- UI: React/TypeScript؛ API: Go/Gin؛ داده: PostgreSQL؛ محاسبات و دریافت: Python؛ دفترهای paper موجود عمدتاً SQLite هستند.
- workspace تغییرات ثبت‌نشده دارد، از جمله `factormix/monthly_paper.py` و رابط/API آن. تغییرات را متعلق به کار جاری مالک بدان. reset، clean، stash، بازنویسی گسترده و stage/commit یکجای آن‌ها نکن. ثبت مبنا به معنی commit خودکار نیست.
- در بررسی قبلی ۱۲۶ تست Python منتخب، ۶۱ تست فرانت، build و Go موفق بودند؛ Go cached بود. lint یک warning داشت. این نتایج برای نسخهٔ بعدی مجوز خودکار نیستند.
- وضعیت ثبت‌شدهٔ paper در ۱۲ نوامبر پوشش ناقص کدال و ۲۱۳ خطای استخراج داشت. وضعیت جدید را بخوان؛ این عدد را ثابت یا معادل تعداد شرکت‌ها فرض نکن.
- پیشرو: `https://online.pishrobroker.ir/Home/Default/page-1`. مالک دستی وارد مرورگر شده و نشست احراز‌شده مشاهده شده است. سبدبان، لینک سفارش‌ها/پرتفو/گردش حساب و فرم معامله دیده شدند. API رسمی، دسترسی برنامه‌نویسی و صحت دادهٔ کامل هنوز تأیید نشده‌اند.
- حساب دارای دارایی قبلی است. دارایی‌های قبلی ابتدا unmanaged هستند؛ در ریسک کل حساب دیده شوند ولی مدل اجازهٔ فروش/بازتنظیم خودکار آن‌ها را ندارد.
- کد آگاه فقط نمونهٔ اتصال قبلی است؛ endpoint یا parser آن را با عوض‌کردن hostname برای پیشرو به کار نبر.

## قواعد کاری برای جلوگیری از دوباره‌کاری

1. ابتدا `AGENTS.md`های قابل اعمال و git status را بخوان. سپس فقط فایل‌های بستهٔ جاری و importهای مستقیم لازم را بررسی کن؛ کل آرشیوهای پژوهشی و داده را وارد context نکن.
2. فایل‌های زیر را در طول کار ایجاد/به‌روز کن؛ مسیرها خروجی پیشنهادی‌اند، نه فایل موجود:
   - `docs/live_broker/STATUS.fa.md`: وضعیت هر بسته، آخرین کار، بستهٔ بعدی و موانع.
   - `docs/live_broker/DECISIONS.fa.md`: قراردادهای فنی مهم و دلایل کوتاه.
   - `docs/live_broker/TEST_EVIDENCE.fa.md`: نسخهٔ کد، دستور، نتیجه، زمان، skip و محدودیت آزمون.
3. وضعیت اجرای کد را از وضعیت gate جدا کن: `IMPLEMENTED` به معنی `PASS` عملیاتی نیست. نتیجهٔ آزمون/gate فقط `PASS / FAIL / UNKNOWN` باشد.
4. در پایان هر بسته checkpoint مستند بنویس و به بستهٔ مستقل بعدی برو. اگر نوبت یا context تمام شد، ادامه دقیقاً از STATUS انجام شود، بدون شروع مجدد ممیزی کل پروژه.
5. برای تغییر حساس دفتر/ریسک/تطبیق، بازبینی مستقل قبل از آماده‌اعلام‌کردن live لازم است؛ خودت PASS مستقل جعل نکن. نبود بازبین مانع کار آفلاین نیست.
6. credential، cookie، token، کد ملی و اطلاعات واقعی دارایی در کد، prompt تحویل، fixtures، screenshot عمومی، Git و لاگ قرار نگیرند. مرجع secret ذخیره شود؛ از فایل‌های حساس صرفاً برای کشف اطلاعات خصوصی استفاده نکن.
7. نسخهٔ منجمد استراتژی، نتایج تاریخی، دفاتر فعال و حساب‌های موجود را مهاجرت یا بازنویسی نکن؛ تغییر مدل/سیاست یا مهاجرت واقعی تحویل جدا دارد.
8. تست‌ها از tmp_path، fixture ساختگی و دیتابیس جدا استفاده کنند؛ اجرای تست نباید ingestion واقعی یا چرخهٔ سفارش را روشن کند. تست شکست‌خورده را صرفاً برای سبزشدن ضعیف نکن.

در مسیر منتخب یک نتیجهٔ readiness ماشین‌خوان با دلیل بساز: سلامت سرویس، داده، استراتژی، تطبیق کارگزاری و مجوز ارسال جدا. کیفیت نامعلوم ورودیِ لازم مجوز ایجاد نکند؛ نقص نامرتبط هم بی‌دلیل کل سیستم را متوقف نکند. برای paper و live حالت مجزا با همان منطق کیفیت و الزامات متناسب اجرا داشته باش.

## بستهٔ ۲ — قرارداد چندکارگزاری و حساب

کار: `BrokerAdapter` با قابلیت‌های اعلام‌شده و نامعلوم‌بودن صریح تعریف کن. حداقل عملیات خواندن snapshot حساب، سفارش‌های باز، fillها با cursor و قواعد ورقه؛ قرارداد ارسال/جست‌وجو/لغو آینده تعریف شود ولی اتصال نوشتنی واقعی ساخته/فعال نشود. ابتدا fake adapter و adapter ساختگی دوم برای contract tests داشته باش.

مدل‌ها: کارگزاری، اتصال، حساب، ورقه، موجودی، قدرت خرید/نقد آزاد/نقد رزروشده، سفارش، fill، سلامت و زمان snapshot. هویت بر اساس `(broker_id, account_id, provider_id)` scope شود. نام نمایشی ورقه کلید تطبیق نهایی نیست. مقادیر پول Decimal یا عدد صحیح واحد پایه با rounding صریح؛ تعداد سهم صحیح؛ واحدهای متفاوت نیازمند تبدیل اثبات‌شده‌اند.

پذیرش: دو کارگزاری با شمارهٔ سفارش برابر مستقل بمانند؛ نشست/lock/cursor مستقل؛ مقدار ناقص unknown بماند؛ سبد خالیِ معتبر با شکست parser اشتباه نشود. افزودن fake دوم نیازمند تغییر موتور استراتژی نباشد.

## بستهٔ ۳ — دفتر تراکنشی مشترک سفارش و منابع

کار: با استفاده از درس‌های دفتر simulation، دفتر execution جدید در PostgreSQL با migration آزمایش‌پذیر بساز. SQLiteهای فعلی را دست‌نخورده نگه دار. intent، risk decision، reservation و outbox به‌صورت تراکنشی ثبت شوند. هر حساب یک worker دارای lease/fencing داشته باشد؛ انقضای worker قدیمی نباید اختیار ارسال باقی بگذارد.

state machine: CREATED، RISK_REJECTED، APPROVED، SUBMITTING، UNKNOWN، ACKNOWLEDGED، PARTIALLY_FILLED، FILLED، CANCEL_REQUESTED، CANCELED، REJECTED، EXPIRED. انتقال غیرمجاز رد شود و همهٔ رویدادها تاریخ و شناسه داشته باشند. برای رویدادهای واقعی دیررس، ترتیب متفاوت و اصلاح معامله قرارداد مستقل تعریف کن.

پذیرش: restart، callback تکراری، fill جزئی، دو writer، intent هم‌کلید با محتوای متفاوت، خرابی قبل/بعد از ارسال فرضی و خرابی پس از commit آزموده شوند. هر fill دقیقاً یک اثر مالی داشته باشد؛ نقد/دارایی دوباره خرج نشوند. پاسخ مبهم شبکه UNKNOWN بماند و ارسال کور تکرار نشود. ادعای exactly-once بین سامانه و کارگزاری بدون پشتیبانی واقعی آن ممنوع است.

نکته: دفتر simulation فعلی ممکن است fill پس از stop/cancel را رد کند؛ در اجرای واقعی باید fill رخ‌داده حتی پس از توقف ثبت شود. توقف جلوی سفارش تازه را می‌گیرد، نه ثبت حقیقت مالی.

## بستهٔ ۴ — کنترل ریسک و محدودهٔ مالکیت استراتژی

کار: gate اجباری پیش از ارسال با نسخهٔ سیاست، سقف حساب/نماد/صنعت، سقف تجمعی چندحسابی، مبلغ سفارش/گردش، نرخ ارسال، موجودی قابل فروش، نقد رزروشده، quote تازه، قیمت/حجم مجاز و توقف ماندگار. حدهای unset یا snapshot نامعتبر مجوز live ندهند. رزرو هم‌زمان حساب‌ها نتواند سقف کل را دور بزند.

دارایی و وجه تخصیص‌یافته به استراتژی از دارایی خارجی جدا شوند. موجودی قبلی روی ریسک کل اثر دارد ولی در برنامهٔ فروش مدل قرار نمی‌گیرد. تخصیص اولیه بدون دستور مالک ساخته نشود. افت حساب با واریز/برداشت اشتباه نشود؛ آستانهٔ زیان ضمانت فروش در صف نیست.

پذیرش: دورزدن gate از API/UI/worker ممکن نباشد؛ دو سفارش وجه مشترک را خرج نکنند؛ فروش دارایی unmanaged رد شود؛ stop پس از restart بماند؛ fill واقعی در حالت stop ثبت شود. هیچ سقف سرمایهٔ واقعی از موجودی حساب یا عدد پیش‌فرض paper حدس زده نشود.

## بستهٔ ۵ — اتصال فقط‌خواندنی پیشرو

کار: مسیر قابل اتکای دسترسی پیشرو و جدول قابلیت‌ها را با شواهد بررسی کن. مشاهدهٔ UI یا یک endpoint داخلی را API رسمی ننام. برای browser از ابزار مجاز همان محیط استفاده کن؛ نشست فعال را به فایل cookie/token تبدیل یا به سرویس ثالث ارسال نکن. چالش ورود طبق الزامات ابزار و با همکاری مالک انجام شود؛ اعتبارسنجی TLS را خاموش نکن.

خواندن کارگزاری از نوشتن داخلی جدا باشد: دریافت → اعتبارسنجی هویت/زمان/واحد/کامل‌بودن → snapshot immutable → diff → پذیرش یا قرنطینه. pagination ناقص، پاسخ خطا با HTTP 200، تغییر حساب، logout، دادهٔ تکراری و خروجی خالی پوشش داده شوند. ابتدا هیچ snapshot جایگزین دفتر مالی یا holdings فعلی نشود.

پذیرش آفلاین: parser روی نمونهٔ ساختگی/پاک‌سازی‌شده و contract tests مشترک موفق. پذیرش اتصال: مشاهدهٔ واقعی خواندن معتبر با زمان ثبت‌شده و تطبیق قابل توضیح؛ اگر دسترسی مناسب مهیا نیست UNKNOWN و ادامهٔ بسته‌های آفلاین. نبود قدرت خرید معتبر برای نمایش قابل توضیح است ولی برای ارسال سفارش مجوز نیست.

خروجی: گزارش قابلیت‌های verified/unknown/unsupported، محدودیت نشست، واحدها و مسیر renewal. نمایش وضعیت «نشست منقضی» بهتر از حلقهٔ ورود بی‌پایان است.

## بستهٔ ۶ — تطبیق حساب و تغییرات خارج از سامانه

کار: نقد، دارایی، سفارش باز، fill، کارمزد و رزرو را بین دفتر و snapshot مقایسه کن. معاملات دستی، واریز/برداشت، سود نقدی، افزایش سرمایه/حق‌تقدم و اصلاح معامله مدل رویداد داشته باشند. رویداد پشتیبانی‌نشده صریحاً مانع شود؛ اختلاف را با overwrite پاک نکن. tolerance عددی از واحد و rounding قرارداد بیاید، نه درصد دلخواه.

پذیرش: اختلاف عمدی به توقف مناسب و هشدار منجر شود؛ اصلاح مستند audit trail را حفظ کند؛ partial snapshot دارایی حذف نکند؛ restore نیازمند تطبیق مجدد باشد. حداقل ۱۰ جلسهٔ واقعی فقط‌خواندنی با گزارش روزانه لازم است تا gate عملیاتی این بخش PASS شود؛ تست آفلاین جای این زمان را نمی‌گیرد.

## بستهٔ ۷ — اتصال مدل منتخب به paper مشترک

کار: هستهٔ تصمیم قطعی FactorMix منتخب را از مجری جدا و به دفتر/ریسک جدید وصل کن؛ منطق استراتژی عوض نشود. حساب paper جدید و ایزوله بساز، نه مهاجرت بی‌اجازهٔ حساب فعلی. قیمت خام و تعداد واقعی برای قرارداد اجرا و قیمت تعدیل‌شده برای پژوهش نقش جدا دارند. صف، توقف، هزینه، تأخیر، partial fill و انقضا در simulator محافظه‌کارانه باشند.

پذیرش: ورودی/سیاست یکسان تصمیم یکسان؛ replay و resume اثر تکراری ندارند؛ اختلاف گزارش‌شدهٔ بازپخش ماهانه با محیط قفل‌شده علت‌یابی شود. تست golden از خود خروجی تازه ساخته و بی‌استدلال پذیرفته نشود. نتیجهٔ شبیه‌ساز با عنوان معاملهٔ واقعی نمایش داده نشود.

## بستهٔ ۸ — پنل کنترل و عملیات

کار: صفحهٔ فارسی ساده برای انتخاب کارگزاری/حساب، سلامت داده، آخرین تطبیق، موجودی managed/unmanaged، سفارش و علت عدم اجرا. توقف هر حساب و توقف کلی در backend ماندگار باشد. preview سفارش شامل حساب، ورقه، سمت، تعداد، قیمت محدود، هزینه و اثر ریسک باشد؛ تأیید با hash ورودی و زمان انقضا و کنترل دوبارهٔ ریسک درست پیش از ارسال طراحی شود. دکمهٔ live همچنان غیرفعال بماند.

run_id/decision_id/order_id در لاگ بدون اسرار؛ هشدار دادهٔ مانده، سفارش UNKNOWN، اختلاف حساب و worker متوقف. DB و runtime با snapshot سازگار، backup رمزنگاری‌شدهٔ خارج میزبان، retention و restore آزمایشی. فایل SQLite زنده با tar ساده قابل اتکا فرض نشود. برای PostgreSQL PITR، base backup و WAL لازم است؛ pg_dump به‌تنهایی کافی نیست.

پذیرش: آزمون انقضای تأیید، دو بار کلیک، جداسازی کاربر/حساب و عدم افشای اسرار؛ مانور قطع DB/شبکه، دیسک پر، ساعت نادرست و restore روی محیط جدا. هدف پیشنهادی RTO=۶۰ دقیقه و RPO=۵ دقیقه اندازه‌گیری شود، نه صرفاً در سند نوشته شود. پس از restore، resume فقط با تطبیق سفارش‌ها و fillها مجاز باشد.

## بستهٔ ۹ — اعتبار مدل و ارزیابی آینده

کار: محدودیت‌های گزارش robustness، جهان ثابت، نمادهای حذف‌شده، زمان واقعی انتشار و انتخاب مدل از تاریخ دیده‌شده را بررسی و دامنهٔ ادعا را مشخص کن. معیار اقتصادی قبل از نتیجه ثبت شود: مرجع هم‌تاریخ قابل سرمایه‌گذاری، بازده خالص، افت، هزینه، گردش و ظرفیت. در این مرحله وزن‌ها و روز بازبینی را برای زیباترشدن نتیجه بهینه نکن.

سایه/paper آینده باید همان gate و دفتر مشترک را استفاده کند. حداقل پیشنهادی: ۶۰ جلسهٔ معاملاتی و ۳ بازبینی واقعی ماهانه، با شواهد زمان واقعی و پوشش سناریوهای اختلال. این معیار عملیات است، نه اثبات سودآوری. دادهٔ گذشته را به جای مشاهدهٔ آینده پر نکن؛ نبودن روزهای کافی یعنی WAITING/UNKNOWN.

## بستهٔ ۱۰ — فقط طراحی گذار به پول واقعی

پس از بسته‌های قبل، checklist آماده‌سازی پایلوت را تحویل بده؛ خودکار فعال نکن. شروط: دسترسی معتبر کارگزاری، حساب مشخص، سیاست ریسک با اعداد مصوب، تخصیص managed، بازبینی مستقل، تطبیق سالم، backup بازیابی‌شده، دورهٔ مشاهده و اجازهٔ صریح شروع.

پایلوت پیشنهادی بعدی: یک حساب، سرمایه و فهرست مجاز محدود، تأیید دستی، حداقل ۲۰ جلسه و یک چرخهٔ کامل تصمیم/اجرا. خودکارسازی و افزایش سرمایه هرکدام تصمیم مستقل بعدی‌اند. هیچ سرمایه‌ای بین حساب‌ها خودکار منتقل نشود و خطای پیشرو باعث retry سفارش در کارگزاری دیگر نشود.

## فرمان‌های مبنای بررسی

از ریشه، در محیط تستی بدون اتصال واقعی:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_runtime_lock.py factormix/tests ranking_research/tests/test_experimental_risk.py ranking_research/tests/test_paper_account_atomic.py qvt_paper/tests/test_execution.py go-app/py/tests/test_broker_agah_offline.py go-app/py/tests/test_broker_captcha_offline.py
```

در `go-app`: `go test -count=1 ./...`؛ روی Linux CI تست race. در `client`: `npm test`، `npm run build` و `npm run lint`. تست‌های جدید بستهٔ جاری را اضافه کن. آزمون PostgreSQL فقط با DSN صریح دیتابیس آزمایشی با نام مجاز پروژه؛ هرگز از `.env` حساب فعال به‌عنوان test DSN استفاده نکن. اگر پیش‌نیاز موجود نیست نتیجه UNKNOWN با دلیل باشد. نصب Docker یا موفقیت CI/restore را بدون اجرا ادعا نکن.

## قالب تحویل هر بسته

برای هر بسته بنویس: مسئله و رفتار جدید؛ فایل‌های تغییرکرده؛ فرمان‌ها و نتیجهٔ واقعی/skip؛ روش rollback؛ محدودیت و gateهای باز؛ قدم بعدی دقیق. تغییرات برنامه‌نویسی را با یک diff قابل مرور نگه دار. ادعای «آمادهٔ پول واقعی» صرفاً به دلیل build یا سبزشدن تست‌ها نکن.

شروع همین حالا: بستهٔ ۰ سپس ۱ و ۲. پس از آن مراحل مستقل آفلاین را طبق ترتیب ادامه بده. هر زمان منتظر نشست یا روز معاملاتی واقعی هستی، همان gate را باز نگه دار و کار مستقل بعدی را پیش ببر؛ تعداد روزها، دسترسی API یا موفقیت تطبیق را جعل نکن.
