# بررسی آمادگی پروژه برای کمک به تصمیم‌گیری در بازار

تاریخ بررسی: ۲۰۲۶-۱۱-۰۴ / ۱۳ آبان ۱۴۰۵، با مبنای زمانی تهران.

## نتیجه

پروژه یک ابزار جدی برای گردآوری داده، غربال، مقایسه و آزمایش کاغذی دارد، ولی یک سیستم کامل و اثبات‌شده برای تصمیم مستقل و اجرای واقعی نیست. گلوگاه اصلی اکنون اتصال قابل اعتماد دادهٔ تازه، مدل، سیاست سبد و پایش عملیاتی است. افزودن مدل و صفحهٔ بیشتر اولویت نخست نیست.

این بررسی شامل خواندن کد و خروجی‌های جاری، درخواست فقط‌خواندنی به سرویس محلی سلامت، بررسی Task Scheduler و اجرای تست‌ها و build است. همهٔ مسیرهای رابط در مرورگر، تمام رکوردهای پایگاه داده، امنیت انتشار عمومی، بازیابی پشتیبان و اجرای واقعی معامله بررسی نشده‌اند. نتیجهٔ قبولی تست، تأیید سودآوری مدل نیست. هیچ چرخهٔ عملیاتی دریافت/معامله، سفارش واقعی یا تغییر در سیاست حساب‌ها از طرف این بررسی اجرا نشده است.

| تحلیل و رابط | غربال، رتبه‌بندی، صورت‌های مالی، نمودار، دیده‌بان، سبد و دستیار | برای بررسی دستی قابل استفاده است، مشروط به توجه به وضعیت داده و مدل هر صفحه. |

## یافته‌های اولویت‌دار

### ۱. سلامت زیرساخت با سلامت تصمیم یکسان گزارش نمی‌شود — اولویت بالا

پاسخ واقعی `GET http://localhost:5000/api/health/shadow` هنگام بررسی:

- `overall = HEALTHY`
- `analytics_status = STALE`
- `score_stale = true`
- `score_as_of = 2026-11-03`
- `read_mode = legacy`
- علت‌های کهنگی: ورود اطلاعات تازهٔ فروش ماهانه، بازار و گزارش‌ها و جلو رفتن تاریخ بازار.

در `go-app/handlers/health.go`، محاسبهٔ `overall` در خطوط ۷۰ تا ۷۶ به سلامت اتصال دیتابیس وابسته است و وضعیت analytics را در نتیجهٔ کلی دخالت نمی‌دهد. بنابراین سالم بودن سرویس، تازه‌بودن امتیازها را تضمین نمی‌کند. تاریخ ارزیابی رتبه‌بندی P1/P3 و امتیازهای غربال نیز باید جدا دیده شوند.

اقدام لازم: سلامت داده/تحلیل، هر مسیر امتیازدهی و آخرین اجرای موفق در یک نمای روشن نمایش داده شود؛ بعد از ورود دادهٔ مؤثر، بازسازی امتیاز و انتشار هماهنگ آن قابل ردیابی باشد.

### ۲. خطای واقعی در اجرای روزانه وجود دارد — اولویت بالا

آخرین `ranking_research/output/paper_month_trial/latest.json` در زمان بررسی، مربوط به ۴ نوامبر ساعت ۱۳:۳۰ تهران است:

- وضعیت کل: `DAILY_ERRORS`.
- P1: `NO_NEW_MARK`؛ بازبینی با `REVIEW_ALREADY_RECORDED`.
- P3: `ERROR / CALENDAR_NOT_READY`.
- Task Scheduler برای `CompanyFinancial-P1P3-30Day-Paper` نتیجهٔ آخر ۱ ثبت کرده است.
- اجرای قبلی `CompanyFinancial-PaperCycle` در ۳ نوامبر نیز نتیجهٔ ۱ دارد؛ این عدد به‌تنهایی مشخص نمی‌کند کدام مرحلهٔ آن شکست خورده است.
- اجرای دستی ثبت‌شده در `.runtime/paper-trial-refresh-status.json` هم `Failed` است: کد خروجی حساب قدیمی ۱ و دورهٔ P1/P3 صفر. متن خطای آن از آخرین خط log مشترک برداشته می‌شود و عملاً بخشی از پیام موفق `MARK_APPLIED` را نشان می‌دهد؛ تشخیص خطای مرحلهٔ قبلی دشوار می‌شود.

اقدام لازم: علت تقویم برای هر حساب حفظ و قابل مشاهده شود؛ گزارش و log هر اجرا/مرحله مستقل باشد؛ موفقیت جزئی و عدم اجرای ایمن از خطای واقعی تفکیک شوند. ردکردن معامله هنگام نبود شواهد معتبر باید حفظ شود.

### ۳. پوشش داده برای رتبه‌بندی کامل نیست — اولویت بالا

فایل فعال `client/public/research/v12-37/latest-ranking.json`، محاسبه‌شده در ۳ نوامبر ساعت ۲۲:۴۶ تهران:

- جامعهٔ ثابت: ۲۵۴ نماد؛ این عدد پوشش کل بازار نیست.
- P1: ۱۵۰ نماد دارای امتیاز و ۱۰۴ نماد بدون امتیاز؛ حدود ۵۹٪ پوشش امتیاز.
- P3: ۱۷۸ نماد دارای امتیاز و ۷۶ نماد بدون امتیاز؛ حدود ۷۰٪ پوشش امتیاز.
- وضعیت صریح: `PREPARATION_UNCONFIRMED`.
- رشد فروش ۱۲ماهه برای ۱۳ نماد، رشد فروش ۳ماهه برای ۴۸ نماد و پایداری فروش برای ۲۵ نماد مشاهده شده است.
- نوسان و مومنتوم ۳۰روزه هرکدام صفر مشاهده دارند، درحالی‌که وزنشان در قرارداد P1/P3 مثبت است. این مشاهده به‌خودی‌خود خطای فرمول را اثبات نمی‌کند؛ بررسی default/mask و اثر اقتصادی آن ضروری است.
- زمان دریافت واقعی آرشیو مالی/فروش ناموجود است؛ خود فایل ادعای اثبات دسترسی تاریخی به این اطلاعات را رد می‌کند.

اقدام لازم: کمبودها بر اساس وزن عامل و اثر روی رتبه اولویت‌بندی شوند؛ برای نمادهای بالای جدول، تازگی و منشأ عامل‌ها قابل بررسی باشد. مقدار مفقود با مقدار مشاهده‌شده یا صفر یکی نشود. سلامت دریافت قیمت به معنی کامل بودن عامل‌های مالی نیست.

### ۴. روش فعال با روش تاریخی یکسان نیست — اولویت بالا

قرارداد تاریخی P1/P3 تک‌سهمی با بازبینی هر ۶۳ جلسه است. در config حساب فعال، سیاست `user-auto-rotation-v1` با بازبینی هر یک جلسه فعال شده است. این تغییر طبق توضیح موجود، درخواست قبلی مالک بوده و وجودش خطای مجوز نیست؛ اما سیاست متفاوتی می‌سازد و نتیجهٔ تاریخی روش ۶۳جلسه‌ای را نمی‌توان عملکرد همین روش روزانه معرفی کرد.

آزمایش از ۲۷ اکتبر شروع شده و فقط ۹ روز تقویمی مشاهده دارد. گزارش مقایسه benchmark هم‌تاریخ ندارد (`UNKNOWN_NO_ALIGNED_VALID_BENCHMARK`) و پوشش اجرای زمان‌بندی به علت نبود سیاست ثبت‌شده در config جاری UNKNOWN است. حالت رسمی ارزیابی آینده نیز در فایل‌های `future-eval-v12-28-*` همچنان `WAITING_FOR_DATA`، بدون تاریخ شروع و با صفر رویداد رسمی است.

دو حساب فعال عملاً سرمایه را در یک سهم قرار می‌دهند. این مسیر یک آزمایش تک‌سهمی است؛ برای مدیریت سبد متنوع و ریسک کل دارایی کاربر کافی نیست. پرشدن سفارش با قیمت پایانی و هزینهٔ فرضی ۰٫۵٪ هر سمت، کیفیت اجرای واقعی را اثبات نمی‌کند.

اقدام لازم: شناسنامه و گزارش عملکرد سیاست روزانه از مرجع تاریخی جدا باشد؛ مرجع مقایسه و محدودیت ریسک سبد مشخص و آزمون آینده با ثبت معتبر زمان دریافت تکمیل شود.

### ۵. بازسازی پروژه از Git کامل نیست — اولویت بالا

بررسی `git ls-files` و `git check-ignore -v` نشان داد فایل‌های لازم در مسیر فعال، از جمله موارد زیر، در Git ثبت نشده و مشمول ignore هستند:

- `ranking_research/future_eval_v12_30/paper_model_review.py`
- `ranking_research/future_eval_v12_30/paper_month_report.py`
- `ranking_research/future_eval_v12_28/engine.py`
- `ranking_research/future_eval_v12_30/canonical_ranking_inputs.py`
- تست `ranking_research/tests/test_paper_model_review.py`

سه فایل اول در زنجیرهٔ import مستقیم دو ورودی `paper_month_trial.py` و `paper_cycle.py` پیدا شدند. علاوه بر کد، چند مسیر به آرشیو و ثبت‌های محلی ثابت وابسته‌اند. بنابراین clone تازه به‌تنهایی محیط جاری را بازسازی نمی‌کند؛ این بررسی نصب تمیز انجام نداده است.

اقدام لازم: کد و تست‌های لازم نسخه‌بندی شوند؛ artifactهای لازم، وابستگی‌ها و روش راه‌اندازی و بازیابی به شکل صریح بسته‌بندی و روی محیط تمیز بررسی شوند. حذف آرشیوها راه‌حل این مسئله نیست.

## نتیجهٔ بررسی فنی این نوبت

| فرمان / مجموعه | نتیجه |
| --- | --- |
| `go test ./...` در `go-app` | موفق؛ بخشی از بسته‌ها از cache استفاده کردند. |
| `npm run build` در `client` | موفق؛ هشدار chunk بزرگ و قدیمی بودن دادهٔ Browserslist. |
| تست‌های CSV و نمای سبد | ۱۰ موفق. |
| `npm run test:indicators` | ۱۵ موفق. |
| ۹ فایل منتخب Python برای حساب، بازبینی، گزارش، preview، تقویم و readiness | ۱۳۴ موفق، ۱ ناموفق. |
| `npm run lint` | ناموفق: ۱۳۳ خطا و ۱۰ هشدار. |

تست ناموفق: `test_paper_calendar_interface.py::test_sales_pit_capability_blocked_for_public_profile`. تست انتظار رد صریح مجوز زمان‌بندی PIT برای تقویم عمومی دارد، ولی تابع پیش از آن سراغ `x.json` ناموجود می‌رود و `FileNotFoundError` می‌دهد. این شکست، ناسازگاری تست و قرارداد جاری را نشان می‌دهد؛ به‌تنهایی اثبات نمی‌کند دادهٔ آینده وارد امتیاز شده است. باید رفتار واقعی با ورودی معتبر و مرز قابلیت تقویم بررسی شود.

کل تست‌های Python و آزمون سرتاسری مرورگر اجرا نشده‌اند. در این بررسی هیچ کد عملکردی اصلاح نشده است؛ build و تست‌ها فقط خروجی‌های معمول خود را تولید کرده‌اند.

## ترتیب پیشنهادی ادامه

۱. رفع خطای تقویم حساب‌ها و گزارش سلامت گمراه‌کننده؛ ثبت دقیق آخرین اجرای موفق هر مرحله.

۲. کامل‌کردن نسخه‌بندی و بازسازی محیط، سپس رفع تست ناموفق و خطاهای lint.

۳. تکمیل عامل‌های دارای وزن و منشأ/تازگی نمادهای مهم، با دروازهٔ پذیرش روشن.

۴. یکپارچه‌کردن شناسنامهٔ سیاست فعال، گزارش مقایسه و کنترل ریسک سبد؛ نگه‌داشتن مرز روشن بین آزمایش و ارزیابی رسمی.

۵. تکمیل شواهد آینده و کیفیت اجرا قبل از هر اتکای مستقل به خروجی یا توسعهٔ اجرای واقعی.
