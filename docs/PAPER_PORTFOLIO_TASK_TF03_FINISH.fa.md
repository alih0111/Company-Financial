# تکمیل محدود TF-03 پس از پذیرش مسیر سالم

محل کار: `D:/RFA/Company-Financial`. ابتدا `docs/paper_portfolio_delivery/task-tf03/review-lifecycle/REVIEW.fa.md` و `boundary-results.json` را بخوان. بازاجرای مستقلِ چرخهٔ ۲۱مرحله‌ای و apply از wrapper موفق بوده؛ موتور و محاسبات را دوباره نساز. فقط چهار دستهٔ زیر را تکمیل کن. رتبه‌بندی واقعی، حساب اصلی، scheduler، O00 و P1/P3 در این کار تغییر نمی‌کنند.

## ۱. ورودی و نتیجهٔ wrapper

- در public، manifest/hash صریح همان invocation مصرف شود. متغیر قدیمی `TSETMC_CALENDAR_MANIFEST` نباید آن را جایگزین کند و public نباید مسیر token/NSCStart را ببیند. با environment ناسازگار و فرمان صریح سالم، کنترل مثبت اضافه کن. برای legacy نیز اولویت ورودی‌ها روشن و backward compatibility حفظ شود.
- در اجرای ایزوله، حذف EvidenceManifest نباید collector را با حساب/خروجی default اصلی اجرا کند. یا پیش از هر acquisition با علت روشن رد کن، یا account/output منتخب را به acquisition یکتای جدید منتقل کن و pointer همان مقصد را بخوان. رفتار انتخابی را با fake acquisition بدون شبکه آزمایش کن. صرفاً توصیهٔ «همیشه این flag را بده» کافی نیست.
- child exit code و outcome اعتبارسنجی را در خروجی ساخت‌یافتهٔ wrapper/cycle نگه دار. NO_NEW_SESSION نتیجهٔ عادی است؛ خطای hash/provider/quality باید حالت blocked/refused روشن بدهد. می‌توان status refresh را بعد از رد اجرا کرد، ولی exit/status نهایی نباید تنها `process_exited_zero` را به‌جای نتیجهٔ محصول نشان دهد. با دادهٔ مردود ادعای validated/official نکن. برچسب عمومی همان فرض عملیاتیِ نسخه‌دار بماند.
- پذیرش: preview سالم، apply صریحِ یک‌باره، no-new-session، manifest/hash مردود، provider ناسازگار و environment قدیمی؛ برای ردها bytes حساب ثابت و علت در خروجی نهایی قابل‌خواندن باشد.

## ۲. اتصال گزارش‌ها به ورودی منتخب و ممیزی واقعی

- در mark، hash و source path حساب از account_path منتخب باشد، نه ثابت ACCOUNT. گزارش پس از mark باید به snapshot نوشته‌شدهٔ همان حساب متصل باشد.
- در status، ranking حساب منتخب را تا گزارش منتقل و منشأ آن را روشن کن. hash ranking اصلی را به‌عنوان شاهد ranking حساب temp ارائه نکن. اگر مرجع عمومی جداگانه لازم است با برچسب جدا ثبت شود. دریافت داده و قواعد اقتصادی تغییر نکند.
- ممیزی نوشتن را از مسیرهای واقعی کد استخراج کن؛ علاوه بر شش فایل محافظت‌شده و ranking، defaultهای `ranking_research/output/paper_cycle`، `client/public/research/v12-38` و مقاصد mark در `client/public/research/v12-36` و سایر خروجی‌های فرزندان را پیش/پس بسنج. hash null برای مسیر اشتباه شاهد حفاظت مقصد واقعی نیست. تغییرات هم‌زمانِ نامرتبط را بدون نسبت‌دادن به این مأموریت گزارش کن.

## ۳. harness و regression بازاجراشدنی بدون تخریب تحویل

- harness را زیر main guard و با output-dir صریح قرار بده؛ pytest از tmp_path یا پوشهٔ یکتای تحت ریشهٔ مجاز استفاده کند. اگر محصول فعلاً مسیر داخل repository لازم دارد، یک پوشهٔ scratch یکتا زیر repo بساز و آن را با شواهد تحویل یکی نگیر. اجرای پیش‌فرض یا import نباید پوشهٔ `offline/` تحویل را حذف کند. مقصد غیرخالی یا رد شود یا زیرپوشهٔ invocation تازه بگیرد. شواهد قبلی و reviewها محفوظ بمانند.
- دو اجرای متوالی harness و یک اجرای pytest نشان بده hash شواهد تحویل و اجرای اول تغییر نکرده است. پس از آخرین run مستند، manifest تحویل ساخته شود.
- برای هر preview دقیقاً outcome همان سناریو assert شود؛ فهرست چهار outcome جای expected مشخص را نگیرد. تعداد جلسات و نبود fill/event نیز بررسی شود.
- حسابداری مستقل را با خروجی واقعی تطبیق بده: shares/gross/fee/cash/NAV/P&L و mark؛ فقط گزارش دو عدد کنار هم کافی نیست. `protected_account_untouched` از hash پیش/پس محاسبه شود.
- replay روز بعد از CLI با clock واقعاً متفاوت یا ساعت سیستم بعدی اجرا شود؛ همان ساعت خرید به command تحمیل نشود. قابلیت در probe مستقل پس از mark کار کرده است. receipt و mark حفظ شوند. آزمون‌های crash/concurrency قبلی را نگه دار و نتیجه را دقیقاً در همان دامنه گزارش کن؛ ادعای تزریق crash در wrapper تنها با اجرای واقعی آن مجاز است.

## ۴. runbook قابل‌اجرا

مدرک پایهٔ ثبت تصمیم را از evidence اجرای بعد از تصمیم جدا کن: ابتدا تصمیم تازه با زمان واقعی ثبت شود، سپس دریافت تازهٔ مناسب مصرف اجرا و preview انجام شود. شواهد قبل از تصمیم را با تغییر timestamp قابل‌قبول نکن. نتیجهٔ no-new-session یا انتظار برای جلسهٔ بعد طبیعی است. فرمان‌های نمونه روی fixture زمانی همین ترتیب را نشان دهند. بستهٔ شروع واقعی می‌تواند به دلیل ranking آماده‌نشده همچنان BLOCKED بماند؛ این اصلاحات به دسترسی تازه یا رتبه‌بندی کامل نیاز ندارند.
