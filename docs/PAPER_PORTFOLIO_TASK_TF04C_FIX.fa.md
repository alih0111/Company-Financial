## A. مقایسهٔ کامل replay و انتخاب درست body

- result کامل parser، status و دلیل رد را برای همهٔ شاخه‌ها مقایسه کن؛ رد صفحات ناقص، نبود انتخاب و نبود body از مقایسه جا نیفتند. در صورت نیاز، normalization صرفاً با قرارداد صریح و محدود؛ حذف مبلغ، واحد، هویت، زمان یا facts برای همسان‌سازی ممنوع.
- صفحهٔ اصلی گزارش، پاسخ‌های redirect و sheetهای وابسته نقش صریح داشته باشند. replay دقیقاً همان main body، receipt اصلی، صفحات و metadata مصرف‌شده در acquire را بخواند. آخرین HTTP200 با tracing مشترک معیار انتخاب صفحهٔ اصلی نیست. برای capture قدیمی، نقش را فقط با شواهد صریح label/URL موجود تعیین کن؛ ابهام را خطا بده.
- mutationهای کپی manifest بازبین را regression کن: مبلغ فروش 1، واحد/هویت متفاوت، outcome مالی موفق ساختگی، علت رد متفاوت باید mismatch بدهند؛ capture اصلی باید بدون شبکه نتیجهٔ فروش و رد مالی موجود را برابر بازتولید کند. mismatch در CLI exit غیرصفر داشته باشد.
- همهٔ outcomeها، از جمله search ناموفق یا اجرا‌نشده، باید قابل بازپخش و مقایسه باشند؛ receipt نبود پاسخ را موفق معرفی نکن.

## B. مسیر واقعی موفق مالی و fixture معتبر

- hash compressed برای ممیزی فایل gzip و hash payload برای قرارداد parser جدا بمانند؛ هر دو پیش از مصرف کنترل شوند. acquire و replay metadata، ورودی صفحات و hash domain یکسان داشته باشند.
- یک fixture آفلاین کوچک و خودبسنده با metadata و body هم‌خوان تهیه کن؛ از دادهٔ محلی معتبر موجود یا fixture مصنوعیِ صریح استفاده کن. fixture آزمون را receipt زنده معرفی نکن. fixture نباید به temp بازبین یا یک گزارش نامرتبط وابسته باشد.
- تست در process تازه، acquire واقعی با opener ساختگی و **parser واقعی بدون mock نتیجهٔ parser** اجرا شود: دو search معتبر → redirect main → حداقل یک sheet لازم با redirect و body متفاوت از main → مالی PARSED_HELD با facts معتبر → فروش PARSED_HELD با مبلغ معلوم → replay برابر کل نتایج.
- assertها باید موفقیت و مقادیر موردانتظار را بسنجند؛ صرف non-null parse یا admission=HELD کافی نیست. بررسی کن main receipt/hash/time با sheet تعویض نمی‌شود. خرابی bytes صفحه نیز رد شود. اتصال شبکه در process والد و فرزند مسدود باشد.
- parser و کنترل publication/identity/unit را برای موفق کردن fixture شل نکن.

## C. receipt و وضعیت نهایی توقف

- timeout پیش از پاسخ، نبود هیچ تلاش به‌دلیل cooldown، و خطای read پاسخ را از «پاسخ کامل hash‌شده» جدا کن. شمار تلاش‌ها، شمار پاسخ‌ها و شمار bodyهای کامل دقیق باشند؛ all روی مجموعهٔ خالی PASS ایجاد نکند. attempt تمام‌شده IN_FLIGHT نماند.
- تست روی acquire واقعی: اولین timeout فقط یک تلاش و manifest جزئی؛ اولین read failure، 429 و challenge بدون تلاش بعدی؛ حالت cooldown با صفر تلاش. نتیجهٔ replay این وضعیت‌ها با وضعیت ثبت‌شده سازگار باشد، بدون ساخت hash یا زمان دریافت برای پاسخ ناموجود.
- توقف‌های کنترل‌شده و خطای parser نباید receiptهای دریافت‌شده را با از دست رفتن manifest حذف کنند؛ اصلاح محدود مسیر نهایی‌سازی کفایت می‌کند، framework جدید نساز.
