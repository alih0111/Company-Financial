# دستور آمادهٔ مأموریت اول: قابل اتکا کردن نوشتن حساب کاغذی

در پروژهٔ `D:\RFA\Company-Financial` فقط این مأموریت محدود را پیاده‌سازی و آزمایش کن. هدف این است که پیش‌نمایش حساب را تغییر ندهد و همهٔ تغییرهای حساب از یک مسیر اتمی، قفل‌شده و سازگار عبور کنند. کار را تا تحویل کد و شواهد کامل کن؛ صرفاً پلن ننویس.

قبل از کار `git status --short` را بخوان و تغییرات موجود را حفظ کن. گزارش بررسی `docs/PAPER_PORTFOLIO_IMPROVEMENT_PLAN.fa.md` را فقط برای وضعیت و یافته‌های مأموریت ۱ بخوان. لازم نیست تاریخچهٔ پژوهش را دوباره ممیزی کنی.

فایل‌های شروع:

- `ranking_research/future_eval_v12_30/apply_paper_fill.py`
- `ranking_research/future_eval_v12_30/register_paper_decision.py`
- `ranking_research/future_eval_v12_30/check_paper_account.py`
- `ranking_research/future_eval_v12_30/refresh_paper_decision_status.py`
- `ranking_research/tests/test_paper_account_atomic.py`

کارهای لازم:

1. با جست‌وجوی محدود، همهٔ مسیرهای نوشتن `paper-portfolio.json` را پیدا کن و نقشهٔ نویسنده‌ها را در گزارش بیاور. یک تابع/ماژول مشترک برای read-modify-validate-write زیر همان قفل انتخاب کن. قفل باید خواندن مبنای تغییر تا commit را بپوشاند، نه فقط write نهایی. از الگوی atomic replace موجود استفاده کن؛ موتور یا DB جدید نساز.
2. اجرای `apply_paper_fill.py` بدون `--apply-fill` باید فقط preview باشد. الان شاخهٔ نبود bar نخستین جلسه، از `record_order_observation` حساب را می‌نویسد؛ شاخهٔ ابهام دیررس هم چنین اثری دارد. preview در هیچ شاخه‌ای رویداد، وضعیت سفارش، شمارنده یا فایل حساب را تغییر ندهد. اگر observe لازم است، رفتار آن صریح و از preview جدا باشد.
3. ثبت تصمیم و mark-to-market و مسیر قدیمی شبیه‌سازی نباید مستقیم و بیرون قفل حساب را بنویسند. مسیر قدیمی را به منطق مشترک وصل کن یا نوشتن منسوخ آن را با پیام مهاجرت روشن متوقف کن؛ دو منطق مستقل fill نگه ندار. قرارداد سفارش فعلی نسخهٔ `1.2.0` و شناسه‌های حساب/تصمیم موجود حفظ شوند.
4. حسابداری خرید باید سازگار باشد: کاهش نقد = مبلغ خرید + هزینه؛ ارزش دارایی در لحظهٔ خرید = مبلغ خرید؛ NAV = نقد + ارزش دارایی؛ سودوزیان اولیه = منفی هزینه. در مسیر قدیمی `check_paper_account.py` سودوزیان صفر ثبت می‌شود؛ اصلاح باید هم خروجی و هم اعتبارسنجی حساب را پوشش دهد. برای پول یک قاعدهٔ روشن و ثابت گردکردن داشته باش و واحد ریال/تومان را مخلوط نکن.
5. قبل از commit، ناوردایی‌های لازم را بررسی کن: نقد و تعداد نامنفی، تعداد صحیح طبق policy فعلی، رویداد/شناسهٔ تکراری بدون دوباره‌کاری، NAV و سودوزیان سازگار با سرمایه و جریان‌های موجود. دادهٔ ناسازگار یا خطای نوشتن نباید حساب قبلی را خراب کند. scope ناوردایی به عملیات پشتیبانی‌شده محدود باشد؛ برای این کار دفتر دوبل یا موتور فروش جدید لازم نیست.

معیار پذیرش:

- برای preview واجد fill، فاقد bar، منقضی و ابهام دیررس، bytes فایل حساب پیش/پس عیناً برابر باشند.
- دو تلاش هم‌زمان نمی‌توانند تغییر هم را گم کنند؛ پس از crash کنترل‌شده قفل آزاد می‌شود و حساب JSON معتبر قدیمی یا جدید است، نه حالت نیمه‌نوشته.
- replay همان fill فقط یک برداشت/یک fill دارد؛ مغایرت payload با همان شناسه به خطای روشن منجر می‌شود.
- یک خرید عددی کوچک با قیمت ریالی و fee معلوم، با محاسبهٔ مستقل نقد/NAV/P&L تطبیق کند؛ تست صرفاً همان تابع پیاده‌سازی را دوباره فراخوانی نکند.
- مسیر ثبت تصمیم و mark هم از writer مشترک استفاده کنند و ناوردایی را دور نزنند.

همهٔ fixtureها و حساب‌ها در temporary directory باشند. شبکه، scheduler، حساب جاری `client/public/research/v12-36/paper-portfolio.json` و دفتر رسمی برای تست اجرا/تغییر نشوند. مدل، وزن‌ها، نماد انتخاب‌شده، مبدأ O00 و قواعد اقتصادی موجود را تغییر نده. فایل‌های خروجی تاریخی را بازنویسی نکن.
